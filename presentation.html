// the problem

AI agents need broad access

  • They read files, run commands, modify code
  • Permission prompts put us back in the loop — approving, reviewing, approving
  • To really leverage them, we need them unblocked
  • They work best when we turn off permission prompts — "yolo mode"
// the tension

The fundamental tradeoff

Full access
Maximum capability
↔
Restricted
Reduced utility

Give them access and accept the risk, or restrict them and lose the thing that makes them useful.

// alternatives

Run them somewhere else?

  • Remote machines, Claude web, GitHub Copilot coding agent — run the agent on someone else's infrastructure
  • If it's working, great — but it's a tradeoff
  • Those tasks run on machines we don't control, without tools we have locally
  • They're also slow — no local iteration speed

There's a balance: hands-off iteration with local proximity. Fast feedback loops, our tools, our environment — but isolated.

// the solution

Isolate, don't restrict

Our machine
→
silo container
→
AI agent
(full access inside)

The agent runs in yolo mode with full capability — but only inside an isolated container with access to our working directory.

// apple containers

Why Apple Containers?

Docker on macOS

  • All containers share one Linux VM
  • VM has broad host filesystem access
  • Containers share that access

Apple Containers

  • Each container = its own VM
  • Only mounted directories visible
  • Own resource constraints

// mounts

Seamless local ↔ silo

  • Tool config dirs (~/.claude, ~/.config/opencode, ~/.config/.copilot) are mounted from our host
  • Read-write for the active tool — sessions persist across container restarts
  • Read-only for other tools — sharing CLAUDE.md files across tools

The workflow

Run silo with a read-only GitHub token for everyday work. When we need write access, pop open a local agent — it picks up the same session. Switch freely between local and silo'd instances.

// caching

Content-addressed caching

  • Images tagged by hash of Dockerfile + tool + build args
  • Only rebuilt when something actually changes
  • Different tools get separate images

Auto-rebuild on tool updates

Background async version check adds zero latency. When a new release is detected, the image hash changes and triggers a rebuild on the next run.

// repos

Repository-aware config

// Apply settings by git remote URL
"repos": {
  "github.com/myorg": {
    "env": ["ORG_API_KEY"],
    "post_build_hooks": ["npm i -g @myorg/cli"]
  },
  "github.com/myorg/special": {
    "env": ["SPECIAL_TOKEN"]
  }
}

Substring matching on remote URLs. Multiple matches merge by specificity (shortest pattern first).
